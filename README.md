# Countersign

Invoice-to-payment reconciliation with document extraction, deterministic three-way
matching, and an approval-gated agent that recommends but never pays.

> **Status: in development.** Sections marked _not yet measured_ carry no numbers until
> the evaluation harness has produced them. Nothing in this file is estimated.

---

## All data in this project is synthetic

There is no real vendor data and no real company data here. The entire corpus — vendors,
purchase orders, deliveries and invoice documents — is produced by a seeded generator in
[`data/generate.py`](data/generate.py) and can be reproduced exactly by anyone who clones
the repository. Vendor names are fictional.

This system has not been deployed at or for any organisation.

---

## The problem

A manufacturing group receives supplier invoices as PDFs and spreadsheets, from dozens of
vendors, in inconsistent formats. Today someone hand-keys each one into a system. Someone
else then checks it against the purchase order and the delivery record, checks whether the
unit price has drifted from what this vendor normally charges, checks that the VAT
arithmetic is right, and checks that the invoice has not already been paid.

The work is slow and repetitive, and the errors it misses get paid out.

Countersign takes the document in, turns it into a structured record, runs the checks a
controller would run, routes anything doubtful to a person, and drafts a recommended
action with every claim linked to the record that supports it. A human makes the decision.

---

## What it does

1. **Ingest** a PDF, XLSX or CSV invoice; hash it, store it, detect its format.
2. **Extract** it into a typed record using a schema-constrained language model call,
   then validate that record arithmetically before anything is persisted.
3. **Check** it deterministically: three-way match against the purchase order and
   delivery, price variance against the vendor's own history, duplicate detection, and
   exact tax arithmetic.
4. **Route** it. Everything passes, or it goes into the human review queue. Nothing
   clears silently.
5. **Recommend** an action — clear, hold, or escalate — with citations, for a human to
   approve or overrule.

## Where the language model is used, and where it is not

The interesting engineering decision in this project is the boundary.

| Layer | How it works | Why |
|---|---|---|
| Document to structured fields | Language model, schema-constrained, with arithmetic validators and one bounded retry | Genuinely unstructured input in formats that vary per vendor |
| Three-way match | pandas, deterministic | A controller must be able to recompute the result by hand and get the same answer |
| Price variance | Median and median absolute deviation, deterministic | Auditable, robust to the outliers it is meant to detect |
| Duplicate detection | Deterministic keys over a committed vendor-normalisation table | Must never be probabilistic guesswork |
| Tax arithmetic | Exact decimal arithmetic | Money is not a floating-point number |
| Recommended action | Agent, reasoning over the check results | Reasoning about findings, not producing them |
| Payment | Human only | Non-negotiable |

The agent holds six read-only tools. There is no write tool and no payment tool, and a
test asserts it.

## Limitations

- The corpus is synthetic. Real vendor documents are messier in ways a generator does not
  invent.
- No OCR. Genuinely scanned, image-only pages are quarantined rather than read.
- Single currency pair.
- No ERP integration. The integration surface is a documented flat export.
